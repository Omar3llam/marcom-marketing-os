## 1. Definition, observation and authority are separate

`scripts/legacy-schema/manifest.v1.json` is a frozen **candidate**, produced from
the exact existing DDL on synthetic PostgreSQL17.11. It records43 columns,
7 constraints,14 indexes, one function and one trigger across four raw tables.
Existing NULL/default distinctions, redundant indexes, constraint names, absence
of raw-table FK/CASCADE and existing function behavior are deliberately retained.
It also pins prerequisite users/workspaces columns and key definitions.
`users.clerkId` remains nullable/unique. Its existing workspace FK is outside the
four raw tables: baseline SQL specifies DELETE CASCADE and no UPDATE action
(native NO ACTION). The Prisma model omits an explicit onUpdate; no whole-Prisma
equivalence is claimed. Production disagreement must BLOCK, not trigger repair.

Physical production owners, grantors, schema/database locale, inherited rights,
PUBLIC/default ACL and historical drift are **UNKNOWN / NOT_TESTED**. The candidate
authority profile (distinct NOLOGIN owner, restricted runtime LOGIN and metadata
auditor LOGIN) is demonstrated only in the synthetic fixture. Bindings are supplied
externally; they do not authorize ownership/ACL changes or prove a production
baseline. A mismatch must stop as UNKNOWN/FAILED/INCOMPATIBLE; do not edit the
manifest to match a live database without independent review and explicit authority.

Source hashes pin the five DDL-owning files plus Prisma schema; all76 shipped
migration names/checksums are independently pinned. Line endings alone normalize
to LF, including the function body. The manifest is not regenerated by the CLI.
Native catalog fields come from pg_catalog, including effective/inherited
capabilities; information_schema's visibility-filtered grants are insufficient.

03B-0 proved NOW-based winner changes and half-commits in synthetic data; no real
account switch is asserted. No diagnostic query reads credentials, customer rows,

Keep all four real tables. Preserve chat/session history and touch behavior,

unchanged; this diagnostic is not canonical evidence or verdict authority.

## 5. Explicit read-only diagnostic

The CLI is **not wired** into install/build/start/worker/predeploy/CI. No dotenv,
ambient DATABASE_URL fallback, Prisma engine invocation or SQL writer is used.

```powershell
# Only after separate authority to inspect the specified non-lab target:
$env:LEGACY_SCHEMA_AUDIT_TARGET_FILE='<reviewed identity-and-role-binding JSON>'
$env:LEGACY_SCHEMA_AUDIT_URL='<explicit diagnostic URL supplied securely>'
node scripts/verify-legacy-schema.js
```

Target JSON has `bindings:{owner,runtime,auditor}` and
`target:{hostname,port,database,login,serverAddress,serverPort,versionMajor:17,tls}`.
`login` must equal auditor, roles must be distinct. `tls` is `verify-full`, or
`disabled-loopback` only for literal loopback hostnames. URL query/fragment
overrides reject. Server identity, session identity and read-only mode are checked
inside REPEATABLE READ READ ONLY; startup default_transaction_read_only is on.
Statement timeout5s, lock timeout1s and connect timeout5s are bounded per operation.
No overall latency/performance guarantee is claimed.

Missing/changed source or manifest and unqualified target → UNKNOWN/exit1.
SQL/connection failure → FAILED/exit1. Exact catalog/history mismatch →
INCOMPATIBLE/exit1. Exact selected candidate match → COMPATIBLE/exit0, with
`LEGACY_NATIVE_DIAGNOSTIC_ONLY` scope, manifest hash/version and DDL source SHA.
Only category names/counts and SQLSTATE are emitted; no raw diff values or errors.
Every shipped history checksum needs one successful, non-rolled-back one-step
receipt; any failed/rolled-back/duplicate/extra/missing receipt blocks. Legitimate
recovery histories require separate reviewed contract evolution, never deletion
to appease the tool. No history-only positive bypasses native comparisons.

COMPATIBLE does **not** certify canonical76 objects, real credentials, runtime
admission, auth, actual target qualification, rolling compatibility or production
readiness. Native canonical safeguards still require their separate audit. Direct
versus pooled production connections, Neon roles and TLS execution are NOT_TESTED.
